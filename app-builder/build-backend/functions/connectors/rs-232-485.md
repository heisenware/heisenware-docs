# RS-232/485

The RS-232/RS-485 serial connector provides an interface for communicating with serial hardware devices and peripherals. It scans system connection paths, configures low-level signaling layouts, manages outbound data lines, and provides asynchronous character stream parsers.

You must create an instance of the `Serial` class to manage connection lifecycles and track separate data stream handlers.

## Static functions

### `list`

Scans the host system and retrieves a summary list of all discovered hardware serial ports. Use this utility to identify the exact path string before initializing an instance configuration block.

#### Parameters

None.

#### Output

Returns an array of objects detailing discovered hardware connections, including device paths, manufacturers, and unique vendor identifiers.

## Instance and control

Constructs a serial interface instance and defines core port connection properties. The underlying physical port remains closed until you explicitly call `open`.

### `open`

Opens the physical communication line channel to the serial interface path configured during creation.

#### Parameters

None.

#### Output

Returns `true` when the hardware port link activates successfully.

### `close`

Closes an open serial port connection channel interface. Any write transmissions currently pending execution buffers inside the channel path will error out instantly.

#### Parameters

None.

#### Output

Returns `true` when the communication link terminates safely.

### `isOpen`

Queries the operational state of the serial connection layer.

#### Parameters

None.

#### Output

Returns `true` if the port link is actively open, otherwise `false`.

### `changeBaudRate`

Alters the sequential signaling data transfer speed mapping configuration for an already open communication port channel.

Returns `true` if the hardware interface speed reconfigures successfully.

#### Example


## Data read and write operations

### `write`

Transmits an unformatted text string payload out through the active serial line channel and blocks until all character bits clear the physical hardware buffers.

#### Parameters

<table><thead><tr><th width="120">Input</th><th>Description</th><th width="100">Type</th></tr></thead><tbody><tr><td><code>data</code></td><td>The alphanumeric text command data payload string to transmit. Supports explicit structural token replacements for whitespace codes. Required.</td><td>string</td></tr><tr><td><code>suffix</code></td><td>An optional text marker string appended to the end of every transmission payload block. Useful for defining uniform termination codes.</td><td>string</td></tr></tbody></table>

#### Output

Returns `true` when all text bits transfer out of the hardware transmission pipeline successfully.

#### Example

This example delivers the text sequence `GET_DATA` combined with a clean carriage return and line feed instruction packet:

```yaml
# data
GET_DATA
# suffix
<CRLF>
```

### `read`

Extracts a static character block size count out of the internal serial incoming data stream storage cache.

#### Parameters

<table><thead><tr><th width="120">Input</th><th>Description</th><th width="100">Type</th></tr></thead><tbody><tr><td><code>size</code></td><td>The total byte count size to fetch directly from the incoming cache tracker. Required.</td><td>integer</td></tr></tbody></table>

#### Output

Returns a text string containing the gathered data character sequence, or returns `null` if the requested quantity of characters hasn't arrived.

## Event listeners

### `onData`

Registers a continuous asynchronous text parser callback listener across incoming serial line streams. The internal listener channels incoming characters into a reassembly engine strategy, executing your script code instantly whenever a rule matching boundary satisfies.

#### Parameters

<table><thead><tr><th width="110">Input</th><th width="190">Key</th><th>Description</th><th width="100">Type</th></tr></thead><tbody><tr><td><code>name</code></td><td></td><td>A unique tracking label identifier used to distinguish this data stream listener. Required.</td><td>string</td></tr><tr><td><code>handler</code></td><td></td><td>The target callback script evaluated on data reassembly. Receives the compiled text string block directly. Required.</td><td>callback</td></tr><tr><td><code>parserOptions</code></td><td><code>delimiter</code></td><td>Emits full data frames when a specific text boundary character matches (such as <code>&lt;LF&gt;</code> or <code>&lt;CRLF&gt;</code>). Default '&lt;LF&gt;'.</td><td>string</td></tr><tr><td></td><td><code>timeout</code></td><td>Emits accumulated data lines once a silent operational pause duration in milliseconds matches this value.</td><td>integer</td></tr><tr><td></td><td><code>byteLength</code></td><td>Emits data blocks systematically once incoming characters fill a static data package byte limit size.</td><td>integer</td></tr></tbody></table>

#### Output

Returns `true` when the event callback link binds successfully to the active parser engine.

#### Examples

Example 1: Delimiter string pattern matching

This configuration works well for devices that conclude every text line frame with a newline sequence code element.

```yaml
# name
line_handler
# handler
<callback>
# parserOptions
delimiter: <LF>
```

Example 2: Inter-byte data silence timeout matching

This strategy suits devices that output information chunks in fragmented bursts without clear termination string lines.

```yaml
# name
burst_handler
# handler
<callback>
# parserOptions
timeout: 50
```

Example 3: Fixed byte count layout matching

```yaml
# name
packet_handler
# handler
<callback>
# parserOptions
byteLength: 16
```

## Tips and tricks

### Asynchronous stream processing design rules
Asynchronous serial transmission channels frequently deliver raw data fragments across inconsistent memory chunk timelines. Using direct synchronous polling approaches via `read` can return chopped, incomplete command lines. To maintain high data reliability, implement the event-driven `onData` method configured with an explicit text `delimiter` or clear `timeout` threshold boundary to process fully reassembled message chunks.

### Variable substitutions for structural whitespace tokens
Industrial serial peripheral hardware components often require hidden non-printable whitespace codes like carriage returns or standard line feeds to acknowledge command endings. The writer utility parses special layout placeholder indicators (`<CR>`, `<LF>`, and `<CRLF>`) present inside your `write` inputs or `onData` configuration matrices, remapping them to raw control strings automatically before delivery.
